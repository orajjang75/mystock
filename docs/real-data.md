# 실제 시세 연동 (11단계)

PRD 8장·10장 오픈 이슈의 결정과, 한국투자증권(KIS) Open API로 실제 시세를 받을 때 알아야 할 한계, 모의 운영 방법을 적는다.

## 1. 결정한 것

| 오픈 이슈 | 결정 |
| --- | --- |
| 분봉 증권사 API | 한국투자증권 KIS Open API |
| 수급 데이터 소스와 확정 시각 | KIS 투자자별 매매동향(`inquire-investor`), 평일 **18:30** 이후 일봉 작업 (`DAILY_SCAN_TIME=18:30`) |
| 저장소 | PostgreSQL만 (TimescaleDB 안 씀) |
| 알림 채널 | 앱 내 + 텔레그램 (실패 시 3회 재시도) |

데이터 소스는 둘로 나뉜다. `ADAPTER=kis` 로 두면 `KisAdapter`가 다음을 맡고, 나머지는 pykrx가 맡는다.

| 데이터 | 소스 | 이유 |
| --- | --- | --- |
| 30분봉 (보유 종목) | KIS 1분봉을 모아 집계 | KIS에는 1분봉만 있다 |
| 일봉, KOSPI 지수 | KIS | 수정주가 |
| 최근 수급 | KIS | 최근 약 30거래일 |
| 오래된 수급 | pykrx (`history_source`) | KIS가 못 주는 구간 |
| 종목 목록, 시점별 시가총액 순위 | pykrx (`listings_source`) | KIS에는 "그날 누가 컸나"를 묻는 호출이 없다 |

그래서 `uv sync --extra pykrx` 가 필요하고(도커 이미지에는 포함), `KRX_ID`/`KRX_PW` 도 필요하다.

## 2. KIS 한계와 백테스트 가능 기간

| 항목 | 한계 | 영향 |
| --- | --- | --- |
| 분봉 단위 | 1분봉만 있다. 호출당 120행, 하루(390분)에 호출 4번 | 30분봉은 직접 집계한다. 봉 시각이 **끝 시각**이라 집계 때 시작 시각으로 바꾼다 |
| 분봉 보관 | 약 1년 | 30분·60분봉 백테스트는 **최대 약 1년**. 그 이전은 불가능 |
| 일봉 | 호출당 100행, 페이징 | 일봉 백테스트는 수년 이상 가능 (pykrx로 더 길게도 가능) |
| 수급 | 최근 약 30거래일, 당일 값은 장 마감 후에만 | 그 이전은 pykrx |
| 호출 제한 | 실전 초당 약 20건, 모의투자 약 2건 (`EGW00201`) | 클라이언트가 초당 호출 수를 지키고, 초과 응답은 대기 후 재시도 |
| 토큰 | 24시간, 발급은 1분에 1번 | 파일에 캐시해 재시작해도 재발급하지 않는다 (`KIS_TOKEN_FILE`, 권한 0600) |

**백테스트 가능 기간 (분봉 기준)**: 오늘부터 약 1년 전까지. 그보다 앞은 KIS에서 받을 수 없으므로, 장기 검증은 일봉으로 하고 30분봉 결과는 최근 1년으로 한정해서 읽는다. 더 일찍 시작하려면 지금부터 수집해 쌓는 방법뿐이다 (모의 운영 기간에 `ohlcv_intraday` 가 같이 쌓인다).

수집 비용 가늠: 100종목 × 60거래일 × 4호출 = 약 24,000호출. 실전 서버(초당 20건)에서 약 20분, 모의투자 서버(초당 2건)에서는 3시간 이상이다. 한 번 받은 과거 날짜는 응답을 24시간 캐시하고 DB에는 upsert 한다.

## 3. 확인하지 못한 가정 (실제 키로 한 번 확인할 것)

이 어댑터는 **실제 KIS 서버에 한 번도 연결해 보지 못했다** (키와 장중 시세가 없었다). 경로와 필드명은 KIS 공식 예제(github.com/koreainvestment/open-trading-api)를 따랐고, 가짜 서버로 동작을 테스트했다. 처음 켤 때 아래를 확인한다.

1. 지수 일봉 tr_id `FHKUP03500100` — 기억에서 가져온 값이라 틀릴 수 있다. 틀리면 A-13(KOSPI 강제 매도)이 멈추므로 `/api/health` 경고로 드러난다.
2. 수급 순매수 금액(`*_ntby_tr_pbmn`)의 단위를 **백만원**으로 가정했다. HTS 화면의 같은 날 값과 비교한다.
3. 분봉 페이징(`FID_PW_DATA_INCU_YN='N'`로 뒤로 넘기기)이 하루 전체를 빠짐없이 주는지.
4. 호출 제한 수치(실전 20, 모의 2)와 분봉 보관 기간 1년. 어긋나면 `KIS_MAX_RPS` 로 낮추고 이 문서를 고친다.
5. 장 마감 직후 마지막 분봉(15:30)이 바로 조회되는지. 안 되면 마지막 30분봉이 늦게 저장되어 지연 리포트에 나타난다.

확인 방법: `ADAPTER=kis`, `KIS_ENV=real`, 키를 넣고 장 마감 후 `make ingest` 를 한 번 돌린 뒤 `/api/health` 와 스크리너의 종목 상세 차트를 HTS와 대조한다.

## 4. 수수료율·거래세율 기본값 (2026-10-19 확인)

`engine/params.py` 의 `RebuyParams` 기본값이다. 출처는 코드 주석에도 있다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 왕복 수수료율 | 0.0354% (`0.000354`) | 한국투자증권 온라인(뱅키스) 수수료 0.0140527% + 유관기관 수수료 0.0036396%, 매수·매도 각각. 한국투자증권 수수료 안내 페이지의 2025.10.27 기준 표 |
| 매도 거래세율 | 0.20% (`0.0020`) | 2026년 세율. 코스피: 증권거래세 0.05% + 농어촌특별세 0.15%, 코스닥: 0.20% |

거래세율 출처는 2025-12-01 머니투데이 기사와 2025-12-26 DS투자증권 공지다. 이벤트·우대 수수료를 쓰면 설정 화면에서 바꾼다. **세율은 매년 바뀌므로 연초에 다시 확인한다.** 손계산으로 검증하는 기존 테스트는 옛 값(0.03%/0.18%)으로 고정했다 (`backend/tests/legacy_rates.py`).

## 5. 모의 운영 (paper run)

실제 시세로 신호와 알림만 내고, 체결 기록은 받지 않는 읽기 전용 운영이다.

- `PAPER_RUN=true`: 체결 기록(POST fills), 재매수 시도, 사이클 포기가 409 로 거절된다. 보유 종목 등록은 가능하다(관찰 대상일 뿐 거래가 아니다). 화면 상단에 "모의 운영 중" 배너가 뜨고 `/api/health` 의 `mode` 가 `paper` 가 된다.
- 보유 종목을 등록해 두면 30분 봉마다 신호가 계산되고 알림(앱·텔레그램)이 온다. 알림 전용 앱이므로 체결 후 사이클이 이어지지 않고, 매도 알림 이후 재매수 단계는 확인하지 못한다는 점은 알고 시작한다. 상태 전이까지 보려면 `PAPER_RUN=false` 로 두고 체결을 직접 기록한다.
- 운영 로그: 스케줄러가 실행하는 모든 작업은 `job_runs` 에 (예정 봉, 시작·종료 시각, ok/skipped/stale/failed, 상세) 로 기록된다. 로그 기록이 실패해도 작업은 멈추지 않는다.

### 일별 리포트

```bash
# API (로그인 필요). 기본은 최근 7일.
curl -b cookie "http://localhost:8080/api/ops/report?from=2026-11-02&to=2026-11-27&format=md"

# 도커: 어제 하루치를 파일로
mkdir -p docs/ops-reports && docker compose exec -T backend python -m app.jobs.ops_report --days 1 > docs/ops-reports/$(date +%F).md

# 로컬 개발: docs/ops-reports/<기간>.md 로 저장
cd backend && uv run python -m app.jobs.ops_report --days 7 --save
```

리포트 맨 위의 **5단계 게이트 숫자**를 본다.

| 숫자 | 뜻 | 게이트 기준 |
| --- | --- | --- |
| 봉 마감 확인 (기대 → 정상 실행) | 거래일마다 30분 봉 마감 13번(09:30~15:30) + 일봉 작업 1번 | 기대 = 정상 |
| 신호를 낼 수 없었던 봉 | 작업이 안 돌았거나(missing), 실패했거나(failed), 시세가 낡아 신호를 막은(stale) 봉 | **0** |
| 수집 실패·지연 횟수 | 분봉·일봉 수집 오류 횟수와 "시세 갱신 지연" 경고 | 원인을 설명할 수 있어야 한다 |
| 보유 종목 30분봉 저장률 | 보유 종목 × 봉 마감 중 DB에 저장된 봉 | 100% |
| 봉 마감 대비 알림 지연 | 알림 생성 시각 − 봉 마감 시각의 p50, p95, 최대 | p95 ≤ 60초 |
| 목표(60초) 이내 비율 | 지연이 60초 이하인 알림 비율 | 100% |

"신호 누락 없음" 은 **봉마다 신호를 낼 수 있었는지**로 판정한다. 신호가 난 봉만 세면 낡은 시세로 신호가 막혀도 누락이 보이지 않기 때문이다. 확인이 필요한 날은 리포트에 사유와 함께 따로 나열된다.

### 로드맵 5단계 게이트 확인 절차

1. `.env` 에 `ADAPTER=kis`, KIS 키, `PAPER_RUN=true`, `DAILY_SCAN_TIME=18:30`, 텔레그램 값을 넣는다.
2. `docker compose up -d --build` 로 올리고, 보유 종목을 몇 개 등록해 둔다.
3. 장 시작 전에 `/api/health` 가 `ok` 이고 모의 운영 배너가 보이는지 확인한다.
4. 평일마다 18:40 이후 리포트를 뽑는다 (cron 예: `40 18 * * 1-5 cd /path/mystock && docker compose exec -T backend python -m app.jobs.ops_report --days 1 > docs/ops-reports/$(date +\%F).md`).
5. 몇 주 동안 위 표의 값이 기준 안에 있으면 게이트 통과다.

## 6. 리허설로 확인한 것과 못 한 것

모의 어댑터와 모의 시계로 하루를 봉 단위로 돌려 리포트 숫자가 맞게 나오는지는 `backend/tests/services/test_ops.py` 가 확인한다 (정상 하루, 봉 하나 누락, 시세 끊김 구간, 95초 지연 알림, 로그 기록 실패, 휴장일). **실제 KIS 시세로 하루를 돌린 결과는 아직 없다.** 위 3장의 가정을 확인하는 것이 그 첫 단계다.
